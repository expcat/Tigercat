## 验收总则

1. **先复现。** 动手前在当前代码上复现。很多条目的证据只有源码和 happy-dom；复现不了的，登记到 [13](13-evidence.md) 的 E09，不直接删行。
2. **修根因，修一处。** Core 的问题在 Core 修；只有一端偏了，就只改那一端。不为了对齐去改另一端本来正确的行为。
3. **配一条会失败的测试。** 补进已有的 spec，修之前失败、修之后通过。表里的「验收」是最低要求。
4. **同步其余几处。** API、交互或样式变了，检查导出、测试、Example 和 `skills/tigercat/references/`。生成物只重跑生成器，命令见 [AGENTS.md](../../AGENTS.md) 的生成物表。
5. **行为变化写进迁移文档。** 调用方能观察到的变化记到 `docs/MIGRATION.md` 或 `docs/MIGRATION-3.0.md`，并带 changeset。
6. **验证命令按改动范围选。** 见 [tests/README.md](../../tests/README.md#按改动范围验证)。测试只在本地跑。没跑的检查不写成通过。
7. **做完就删行。** 完成的行从任务表里删掉，记录进 `CHANGELOG.md`。本目录不存完成历史。

## 证据口径

- 审查用的是内置浏览器（IAB）的隐藏会话。环境中途不可用，3364 个视口格里视觉 2772 格、键盘 2832 格是 blocked。
- basic 组 32 个组件里 28 个是 complete，有截图和按键记录。layout 组有 3 个（AspectRatio、Card、Carousel）。其余七组没有截图，条目来自源码阅读、定向测试、SSR 输出和 happy-dom 探针。
- 因此 P2、P3 的条目里可能有在真实浏览器里不成立的。总则第 1 条就是为这个设的。
- 审查过程中报告对彼此做了归并：后审的组件确认前面的发现同样适用时，不另立编号。本计划的「并入」「同验」清单来自这些归并记录。
