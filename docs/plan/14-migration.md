# 14 迁移文档策略

彻底重构，禁止补丁。条目一次做到新结构：不留弃用别名、双写 prop、运行时兼容分支，或只改半边行为的收尾。每个改到的组件，同一批同步 `skills/tigercat` 与 `examples`。测试只在本地跑，不写入 CI / workflow。

本步不改 `docs/MIGRATION.md` 和 `MIGRATION-2.5.md` 至 `MIGRATION-2.8.md`。下面约定执行 3.0 时怎么写。

## 目标

- 调用方能按部分看到 3.0 行为变了什么。
- 全部任务完成后，只剩一篇总结式终稿：每个公开组件一种写法。
- 文档、skill、examples 描述同一套 API。

## 非目标

- 不写兼容层的用法，不写「旧 prop 仍可用」。
- 不把 3.0 的破坏性变更回写成 2.x 分册里的补丁说明。
- 不在运行时保留弃用别名，即使用迁移命令可以改写 import。

## 增量

执行开始后新建 `docs/MIGRATION-3.0.md`。每完成一个组件或一条会改变默认结果的任务，追加一节，只写：

- 组件名
- 旧的默认行为，一句话
- 3.0 的唯一行为
- 要改的导入名或 prop（若已删除）

2.5 至 2.8 的分册保持为历史档案，执行过程中不往里追加 3.0 条目。`MIGRATION.md` 在终稿之前可以只加一句「3.0 进行中，见 MIGRATION-3.0.md」，不复制正文。

会改变默认结果、增量里应出现的例子：条件分支的走向、必填是否真的校验、导出前缀、日期往返、空值形态、已删除的公开名字。纯内部重构且调用结果不变的，不单开一节。

## 终稿

W11、全部优化和增强完成之后，把 `docs/MIGRATION-3.0.md` 改写成总结，按组件排列：

- 每个公开组件只留 3.0 的写法
- 删掉过程性的「这一批先改了什么」
- `MIGRATION.md` 用一节指向这篇终稿，并说明 2.x 分册是档案

此时 skill 与 examples 已经随组件更新。终稿不另维护第三套 API 说明，只记录从 2.x 走到 3.0 时调用方要改的地方。

## 迁移命令

T12 E5 的 `tigercat migrate` 只改导入说明符和已经删除的兼容名字。它不在运行时留下旧 API，也不代替这篇终稿。命令覆盖的名字列表来自 `public-components.mjs` 里记录的删除项，不手写第二份。
